## Step 0 — CNI pre-check (not in the published reproducer; it should be)

Before trusting any "blocked" result, confirm this cluster's CNI enforces NetworkPolicy at all.
Two busybox pods in a throwaway namespace, one selected by a `egress: []` policy and one not:

```
$ kubectl exec -n netpol-precheck control -- timeout 8 nc -zv -w 5 1.1.1.1 443
1.1.1.1 (1.1.1.1:443) open
exit=0

$ kubectl exec -n netpol-precheck selected -- timeout 8 nc -zv -w 5 1.1.1.1 443
command terminated with exit code 1

$ kubectl exec -n netpol-precheck selected -- wget -qO- -T5 https://1.1.1.1/
wget: can't connect to remote host (1.1.1.1): Connection refused
```

kube-router **rejects** rather than drops, so a blocked probe returns in ~1s, not at the timeout.
Enforcement confirmed. Every result below is interpretable only because this passed.

### New observation this run: the *Sandbox CR* does carry the template-ref-hash, even on v0.5.0

```
$ kubectl get sandbox -n repro-warmpool-label --show-labels
NAME               LABELS
repro-pool-45h28   agents.x-k8s.io/launch-type=warm,agents.x-k8s.io/sandbox-pod-template-hash=5cbedcf0,agents.x-k8s.io/sandbox-template-ref-hash=0d20a304,agents.x-k8s.io/warm-pool-sandbox=a2106d30
repro-pool-jfqg9   agents.x-k8s.io/claim-uid=65c8ac36-9338-4a93-8b4a-dc8edbfdb481,agents.x-k8s.io/launch-type=warm,agents.x-k8s.io/sandbox-template-ref-hash=0d20a304
repro-pool-vlfkq   agents.x-k8s.io/launch-type=warm,agents.x-k8s.io/sandbox-pod-template-hash=5cbedcf0,agents.x-k8s.io/sandbox-template-ref-hash=0d20a304,agents.x-k8s.io/warm-pool-sandbox=a2106d30
```

The hash the generated policy selects (`0d20a304`) is on every **Sandbox** object and on **no
pod**. The generated policy is therefore not selecting a nonexistent value — it is selecting the
right value on the wrong object kind. That is the precise shape of the v0.5.0 bug, and it is what
the v1.0.x adoption change addresses (see the v1.0.2 run record).

Claiming also swaps labels on the Sandbox CR: `warm-pool-sandbox` and `sandbox-pod-template-hash`
come off, `claim-uid` goes on.

## Corrections to the reproducer, made as a result of this run

1. **`kubectl wait --for=condition=Ready pod --all` in step 1 fails immediately** with
   `error: no matching resources found`. The warm pool takes ~9s to create pods and `kubectl wait
   --all` does not wait for resources to exist. Replaced with a poll that waits for the pods to
   appear first.
2. **`sandbox-router` is not a prerequisite.** The claim bound and reported
   `Ready/DependenciesReady` with only the controller and CRDs installed. The README listed the
   router under prerequisites; it is only needed to *connect into* a sandbox, which this
   reproducer does through `kubectl exec` instead.
3. **A CNI pre-check belongs in the reproducer**, ahead of step 5, for the same reason the parent
   report gives for the control pod: without it, "blocked" is unattributable.
